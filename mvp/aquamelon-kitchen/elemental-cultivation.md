# 水瓜厨房 MVP：七元素培养与水瓜汁混合

本文件只记录七元素培养表现、性状与待开发的下游玩法。权威养分、生命周期、单一果实账户与采摘语义见 [七元素养分与生长系统](growth-system.md)；反应数值见 [果实元素反应结算](fruit-reaction-settlement-design.md)。最终 Flavor 在品尝时生成，不使用果实元素比例直接作为成品风味合同。

**当前口味合同**：[七元素与反应风味](taste-model.md) 直接读取自由元素与所有现存反应产物；旧27项Taste数值结构已弃用，入口/中段/回味仅用于AI描述顺序。

**当前已确认的果实合同**：花苞出生即开始同一份 `E_free[7]` 累计，12G开花、40G青果、90G成熟；成熟后的合法反应可以产生 `Products[]`，花期元素全部可食，采摘完整继承。现有 Web／千星运行时是否已迁移需要分别验证，本文件不授权运行时改变。

**植物如何从土壤获取元素、如何形成 Growth Vector、如何经历 Stage、叶片 / 花 / 果如何持续学习亲和与分流养分，已经迁移到 [七元素养分与生长系统](growth-system.md)。本文件不再作为这些生长规则的 source of truth。**

第一版的培养链已经更新为“土壤储备 → 树体储备 → Growth Tick → 器官生长”。

```text
浇灌元素到土壤
↓
土壤形成七元素储备并持续蒸发
↓
树按 Stage 吸收能力、RootPreference 与单元素饱和规则从土壤吸收
↓
树体内部形成七元素 Reserve
↓
Growth Tick 消耗 Reserve 并形成七元素 Growth Vector
↓
Tree 先向各 Leaf 做第一层预算分流；每片 Leaf 再只在自己的预算内向附属 Flower / Fruit 分流
↓
器官按自身亲和、Stage 与损耗继续生长
↓
Growth / Affinity 决定颜色与形态
↓
采摘后的活体器官先转换为独立 world Material，再由已确认的材料加工关系进入料理链
↓
玩家根据结果反向调整下一轮培养
```

生长与养分流的 source of truth 见 [七元素养分与生长系统](growth-system.md) 和根目录 [Growth Tick](../../docs/plants/growth-tick.md)。

当前2D Lua参赛版按已确认的§6.18支持全部已纳入的元素反应；不扩展复杂料理、多人互动、顾客经营或生产系统。

相关背景见 [千星奇域水瓜树](setting.md) 和 [水瓜厨房 MVP 需求](requirements.md)。

## 七元素培养数据与亲和

RootPreference 决定植物从 Soil 吸收哪些元素，Growth Affinity 决定各元素如何参与单通道上限与 Growth 转换。时间与养分模型共用 [uh 统一规范](../../docs/plants/uh-time-unit.md)，不能另行在本文件定义单位。

### RootPreference 与 Growth Affinity

旧版把同一组 Affinity 同时用于“从来源提取元素”和“转化为 Growth”。这一语义已经废弃。

当前正式分为两类参数：

#### RootPreference

RootPreference 表示 Tree 根系在混合 Soil 中“更容易吃什么”。

```text
TREE_RootPreference[7]
range = 0~1
```

它只用于：

```text
SOIL_Elems
→ TREE_Elems / Reserve
```

RootPreference 不参与 Growth 转换、不参与当前 Affinity 连续学习，也不能通过大于 1 来提高吸收效率。

RootPreference 已确定为`[0.80,1.00,0.85,0.75,1.00,0.70,0.90]`（七元素统一顺序），不再作为待定参数。

#### Growth Affinity

Affinity 保留原有“吃进去以后长得多有效”的语义，并允许超过 1。

当前已有基础值继续作为 Growth Affinity 参考：

| 元素 | Tree | Leaf | Flower / Fruit |
| --- | ---: | ---: | ---: |
| 火 | 0.85 | 0.75 | 1.00 |
| 水 | 1.15 | 1.10 | 1.00 |
| 风 | 0.90 | 1.00 | 1.00 |
| 雷 | 0.75 | 0.85 | 1.00 |
| 草 | 1.20 | 1.30 | 1.00 |
| 冰 | 0.70 | 0.90 | 1.00 |
| 岩 | 0.95 | 0.80 | 1.00 |

Stem 已退出当前器官模型，不再保留 Stem Affinity。

Growth Affinity 用于：

```text
Reserve → Growth 转换：
使用完整 Affinity

未定型 Stage：
在 Base Affinity 上持续学习

Stage 变化：
固定当前 Effective Affinity
→ 作为下一 Stage 的 Base Affinity
```

因此不再存在：

```text
从来源提取：
min(Affinity, 1)
```

这一旧规则。

### 浇灌与容量归一化

玩家主动富集随机七元素之一的纯元素球，**初始量固定50V**；收集时仅把当前未衰减的实际余额加入 Soil。Soil总容量**1000V**，允许收集瞬间超量，下一结算开始按`1000/ΣSoil`等比例压缩七维超额量。之后按0.99/uh蒸发并由根系吸收；球按0.25uh半衰，不因UI刷新额外衰减。

### 统一 uh 时间与养分流

本文件中的培养速度统一使用 [uh 等效小时](../../docs/plants/uh-time-unit.md)，吸收上限用 V/uh，生长使用器官实际累计 Growth[7]。Seed / Seedling 直接从根系吸收形成 Growth；Sapling 先进入 Reserve，再由当前 Reserve×Tree Affinity 动态生成本次预算。每片叶优先取用本次预算、未用额度返还 Tree；花果只能从所属母叶本次所得份额取用。

元素锁定对土壤、Reserve 或亲和的具体作用尚未设计，不属于当前培养公式。

## 培养结果与玩家体验目标

七元素培养不是“输入一个配方就得到固定产品”的系统，而是一个有随机扰动、可观察、可学习并逐渐可控的培养过程。

### 普通玩家：随机输入得到普通水瓜

完全不了解系统的新人玩家，可以把随机刷出的元素球都投入土壤。

目标结果：

- 七元素输入长期相对分散；
- 最终不形成明显单一元素主导；
- 产出以普通水瓜为主；
- 每个果实仍因随机输入略有差异，但完整味道向量应与普通水瓜基线大体接近。

随机输入仍允许偶然形成偏水、偏草等方向，因此新人有机会偶然获得一两个 Hydro Aquamelon、Dendro Aquamelon 等特殊果实。它应当像“第一次发现培养系统存在”的惊喜，而不是无需理解就能稳定复制的配方。

### 定向培养：有效，但不是免费收益

玩家如果只投入某一种元素，应当能够明显推动该元素性状。

但单元素不能独自撑满 Tree 的完整吸收吞吐量：

```text
只供给单元素
→ 目标元素持续富集
→ 该元素达到自身有效吸收饱和
→ 其他元素无法补足根系吞吐
→ 总吸收 / 生长速度明显下降
```

因此“只浇一种”是简单、有效但低效的定向培养方法。

更熟练的玩家需要在：

```text
目标元素占比
×
其他元素提供的生长支撑
```

之间寻找配比。

### 外形与风味并非同一标签

- 未出现反应产物时，所有非零元素都参与Lua计算的七维归一混色；没有“显著元素”“主元素超过50%”等表现阈值。
- **第一种实际生成的反应产物**及触发方向锁定整颗果子的**名称和完整图标**。多重反应仍保留第一次的形态；首产物之后被进阶消耗，也不回改外观。
- 风扩散只改变自由元素，不生成独立Swirl产物，因此不会单独锁定反应果名称。
- 最终品尝读取全部**当前**自由元素与反应产物；后续反应风味不能因首次外观而被丢弃，被消费的旧产物不再重复计味。

### 高纯度不等于高品质

接近完全纯净的单元素水瓜应当：

- 很难稳定培养；
- 因单元素吸收饱和而成长较慢、产量偏低；
- 风味和性状非常极端；
- 未必适合直接食用；
- 更可能作为特殊料理、加工或工业型原料。

因此培养的目标不是简单把某个元素堆到 100，而是根据用途寻找合适的组成。

### 玩家如何掌握系统

玩家通过生长颜色、首次反应果图标和名称推断培养结果；内部七维数值仅在Debug和AI提示词显示。初始亲和度决定底色，实际Growth逐渐叠加新的元素混色，不能改用树Reserve主元素“一键选色”。

## 元素颜色与 Lua 显色

七元素主体色及 PNG 名称见[元素视觉参考](../../docs/visual/element-reference.md)。显色按七维向量加权混合，不设置额外阈值。

- 将器官出生/阶段固化后的 `BaseAffinity[7]` 归一成权重`a[i]=Affinity[i]/ΣAffinity`，得到`C_base=Σa[i]RGB[i]`。
- 将当前器官实际 `Growth[7]`（生殖器官使用`E_free[7]`）归一成`g[i]=Growth[i]/ΣGrowth`，得到`C_growth=Σg[i]RGB[i]`。
- 成长向量非零：**`C=0.70C_base+0.30C_growth`**；零Growth时只显示底色。**所有正量七元素立即参与**，无选最大分量、无50%显色门槛。
- 一旦首次产物锁定果形，改用对应**整果图标和名称**，仅把剩余`E_free[7]`归一混色以**30%强度**叠加到产物图标；自由量全零则不叠色，Products不拆回原元素再上色。
- 七维加权RGB、图片颜色和已导入图片ID切换**全部由Lua控制**；编辑器预置静态图片/控件与有效`imageSource/imageId`，不能传仓库PNG路径假装资源ID。颜色展示不增减真实世界资源。

## 果实与后续料理数据边界

当前果实生长与反应仅使用**单一权威物质账户**：

```text
FlowerBud：E_free[7] 自0开始
→ 累计12G：Flower
→ 累计40G：GreenFruit，锁定果实 Affinity
→ 累计90G：MatureFruit，阶段锁定
→ 成熟时与合法后续富集事件：E_free[7] + Products[]
→ 采摘青果／熟果：完整继承现有物质账户
→ 2D Lua参赛版：一个熟果一键转成一份汁，全部物质账本唯一转移
→ 最终品尝：用当前E_free及全部Products解释元素与反应风味
```

所有花苞／花期 Growth 均成为可食果实物质。生殖物质在结果时不清零、不复制，也没有另一份结果后才开始的元素库存；成熟后反应改变自由元素和产物数量时不使阶段回退。物质量由 `M = ΣE_free + ΣProducts.amount` 派生；**不能再使用旧的元素占比作为最终 Flavor 的计算合同**。2D Lua参赛版已确定一果一汁（不另生成瓜壳/果肉），其它多产物路线仍需独立分账。成熟后按`0.5×clamp((150-M)/60,0,1)`倍率线性富集，150G不是反应物质硬上限；最终品尝只读果汁快照。
