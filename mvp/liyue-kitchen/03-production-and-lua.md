# 七格洞天、加工链、订单与 Lua 实施 v0.4

## 1. 生产链

```
凝聚元素球（随机元素、50V）
  → 玩家收集 / 配置浇灌
  → 七格蜂巢洞天中的指定地块 [每格独立 Soil[7]]
  → 每格最多一棵植株 [Growth / Reserve / Leaf / Flower / Fruit]
  → 夜间时间推进 [全局 K uh, 各地块独立结算]
  → 完整水瓜材料 [E_free[7], Products[]]
     ├→ 水瓜订单交付 [完整果实]
     └→ 剥壳 → 果肉 → 榨汁 → 原汁 → 装杯 → 果汁订单交付
  → 探索发现 / 技术研究 / 样本收藏
```

植株领域计算复用 `../aquamelon-kitchen/02-data-and-balance.md`、`03-growth-and-harvest.md`、`04-elemental-reactions.md`、`05-sensory-identity.md`、`06-flavor-contract.md`。单对象状态及时间仍按已确定顺序进行，允许多个地块拥有各自合法 Soil/Plant 状态，但绝不共享一份隐式 Reserve。

## 2. MVP 明确加工流程与账本（待 Lead 审批）

两种订单成品：`MatureAquamelon`（完整水瓜）、`AquamelonJuiceCup`（装杯果汁）。

MVP 的加工操作仅有 **剥壳、榨汁、装杯**，全部在白天执行，动作成功后即时产生物品。无煮锅、研钵、加热/研磨和复杂料理。

```
完整果实 --[剥壳]--> 去壳果肉 + 果壳
去壳果肉 --[榨汁]--> 未装杯果汁
未装杯果汁 + 空杯 --[装杯]--> 杯装果汁
```

最小提议物质约定：
- 完整水瓜可直接交付水瓜订单。若进入加工，则消耗该完整果实对象并生成新的 `PeeledFlesh` ID 和 `Shell` ID。
- **七元素账本整份随可食果肉转移**：`E_free[7]` 和 `Products[]` 在 `MatureAquamelon → PeeledFlesh → RawJuice → AquamelonJuiceCup` 每一步完整转移且只能存在于一个有效载体，完全继承感官和形态来源事实。原对象在后继生成时消耗。榨汁遵守**一果一份汁**。
- `Shell` 是具有独立 ID 的物理副产物，但 MVP **不携带元素 G 账本**、不参与进一步加工或订单；这只是未建立果壳分配模型前的保守方案，日后若加入可利用果壳需另定分账和风味影响。
- 空杯作为容器对象提供（初始库存或后续常规补给，不进入复杂经济），装杯消耗一个空杯和一份原汁，产出一份带容器状态的成品。原汁和成品绝不能同时存在。
- 加工不调用新的七元素反应结算或偷偷改变 G 总量；仅原生长/反应模型允许特殊风扩散净增减。加工每步生成可核验来源的操作事件。
- 水瓜订单拒绝果肉/果壳/果汁；果汁订单拒绝原汁/未剥壳原果，验收需为杯装成品。
- 玩家可以把任何合法可移动物件放在水晶球地面、仓储区或工作台；位置变更只更改容器/坐标，不复制物件。

此最小分账使新的加工步骤可玩，同时不需要虚构果壳的七元素比例。待 Lead 批准后成为新 MVP 加工合同；未来如果新增煮锅、研钵、料理或果壳再利用须分别定义新配方。

## 3. 领域状态建议

```lua
Game = {
  day = 1,
  phase = "DAY_WORK",
  dayAdvanceUH = 24,     -- 候选 pacing，待验证
  dayCondenseUsed = 0,
  dayCondenseLimit = 0,   -- 初值由配置/技术决定
  plots = {},             -- 固定 7 格（包含 unlocked），已开垦格各自 Soil/Plant
  looseBalls = {},        -- 全洞天每日共用 N 次凝聚，球有稳定 id 与 V
  items = {},             -- 材料/容器/副产物 ID + location: ground/storage/workbench
  machines = {},          -- MVP 剥壳、榨汁、装杯；未来设备夜间进度
  visitors = {},          -- 访客/对话
  orders = {},            -- acceptedDay/dueDay/itemKind/quantity/state
  adeptalEnergy = { balance = 0, earnedTotal = 0, spentTotal = 0, rewardedIds = {} }, -- 洞天仙力唯一可消费账本
  discoveries = {},       -- completed + evidence
  tech = {},
  productionPlans = {},
  eventLog = {},
}
```

此结构用于标明单一状态所有权，不是强制实现为一个巨大模块。实际 Lua 模块按已有 Domain / UI / Taste 分离增加 Visitor / Discovery / Production / DayController / Progression，避免多套账本。**洞天仙力属于解锁/养成资源，独立于七元素 V/G 账本**。所有奖励按事件/来源 ID 去重，升级消费原子扣费与永久生效，详见 [04-adeptal-energy-and-plots.md](04-adeptal-energy-and-plots.md)。运行时 GUI 只投影 Game，按钮调用经校验的领域动作。

日结顺序建议：
1. 验证结束日指令，快照运行中生产配置和库存；
2. 按时间顺序推进每个地块已有 `advanceUH(K)`，保留同一模型日界事件（如每日 04:00）及真正输入/反应的先后；
3. 如未来启用夜间设备，用同一 K 推进设备生产工序；MVP 手动剥壳、榨汁、装杯均在白天即时处理，不新增夜间产物；
4. 更新订单：截止日 D 的当天白天可交付，结束第 D 天后未完成则过期；从真实事件判定探索完成，冻结报告与证据，更新科技/委托状态；
5. 原子写入次日状态并刷新 UI。失败时不得出现部分结算、重复领奖或材料复制。

具体领域/生产结算先后涉及设备消耗哪些活体产物，必须在配方设计时锁定，不可一概假定所有设备同于夜间最后结算。

## 4. UI-driven 实施顺序

**正式开发工作按 [05-ui-driven-implementation.md](05-ui-driven-implementation.md) 的 UI-00～UI-08 切片进行。** 每个任务以可见 UI 物体、玩家动作、领域 Guard、真实 Game 状态变化和可见反馈为输入/验收；内层 Lua 逻辑随对应互动开发，不单独以「编写完模块」作为完成标志。首个交付是千星实机可点击的柜台、水晶球七格和访客赠种→播种，而非提前开发整套 Domain/经济/订单后才做 UI。

编辑器静态布局与对象命名首先固化到绑定清单；Lua 域保持唯一权威状态。没有实际验证的拖拽/图谱缩放/API，用选择物品再点击目标或静态图谱控件作可玩降级。所有完成标记须有当前关卡真实截图/录屏 + 操作步骤 + 领域状态/关键事件证据。详细 checklist 不在本文件复制，防止维护两份互相冲突的进度。

## 5. P0 体验闭环建议

首个可玩切片目标：

- 一个 16:9 固定柜台，至少一位剧情仙人、一位后续访客；访客能递交种子及委托。
- 屏幕中央一只**七格蜂巢排列的洞天水晶球**，七格均可见且有稳定 ID，初始仅部分已开垦；只有已开垦格允许独立种植，每格最多一棵树；每天全洞天 N 次随机凝聚，可将物品暂存在球内地面。
- 玩家可手动结束日，结算 K uh；次晨可见真实 Growth 阶段和重要事件。
- 同一原有数值系统能生成至少一枚合法 MatureFruit；可直接交付完整水瓜订单，或依次**剥壳→榨汁→装杯**形成一份合格果汁并交付果汁订单；每步 ID 和七元素账本连续且无复制。
- 右侧常驻委托及探索入口，委托只有「完整水瓜」「杯装果汁」两类，含按游戏日到期的状态；图谱至少覆盖种植→成熟→水瓜交付及加工→装杯→果汁交付，另有隐藏反应节点。
- 玩家从有意义的访客互动、有效种植周期、采摘成熟果和成功交单中获得洞天仙力；至少能**消费仙力解锁一块外围地格**，并在其独立种植与完成夜间结算。重复领奖不可行。
- 玩家经历重复收集后，可**满足探索/劳动条件并消费仙力**解锁一个有效便捷工具（P0 建议批量收集）。
- 每一个达成图谱条件的节点，都能够指出对应的真实游戏事件与证据。
- 至少一份「夜间结算记录」可以在 Debug 中复现其实际 Soil/Reserve/Growth/产物变化；不以 24 倍产量公式伪造结算。
- 完成新开档→接受种子与带截止日的水瓜订单→七格之一种植→多夜生长→收获→交付，随后剥壳→榨汁→装杯→完成果汁订单→图谱发现的手动端到端验收。验证恰在截止日可交、次日则过期、逾期后可获得新单。

**P0 明确延期**：煮锅、研钵、复杂料理、七格批量自动化、大规模扩展地块、全部剧情仙人、200+探索节点、复杂经济、与外部 AI 联网、多人/服务端节点图。保留旧版果汁 AI 品尝提示词作为后续可接入功能，不要求为了新交互当即完成跨应用复制。

## 6. 平台与编辑器边界

本项目已实机验证：Lua 在 `ClientUIContainerControl` 宿主修改文本、PC 鼠标点击监听；Seed→Sapling 已有计算切片证据。未验证：大量可缩放图谱、稳定动态物品拖动、复杂层叠窗、动态图片替换、持久存档与高数量实体。因此 P0 应优先验证这些接口中最关键的 **界面视图切换、真实操作 ID、日结性能、存档**；若拖动不可用，采用选择物品→点击设备。

静态 UI、角色立绘、器具图片和位置由创作者在千星编辑器布置；Lua 管理状态、操作判定、时间推进和显示内容。禁止把 Web 前端、Node 后端或旧节点图编译流程引入当前纯 Lua 单机实现。

## 7. 设计关口

实现前仍需 Lead 锁定：
- `K` 与初始 `N`，据原有真实数值模拟首果天数、不同随机供给轨迹；首单截止日要覆盖合理首果变动和玩家学习时间；
- 七格蜂巢的稳定 `plotId`、初始开垦格数（候选中心一格）、新格仙力费用、独立原单株领域状态、球内地面物件位置/仓储/工作区容器移动；
- 成就触发事件的最小契约、隐藏节点揭示规则；
- MVP 剥壳→榨汁→装杯的最小物质流、零 G 果壳副产物提议、空杯的初始供给；
- 桌面物品/访客/窗口在千星 Lua 中的最小真实交互；
- 洞天仙力奖励金额、奖励事件去重/交易账本及首格扩建与首项科技的费用；
- 游戏日跨会话存档/读档的实际平台能力。
