# 食材生产、局内数据与 Lua 实施 v0.1

## 1. 生产链

```
凝聚元素球（随机元素、50V）
  → 玩家收集 / 配置浇灌
  → 洞土地块 [Soil[7]]
  → 植株 [Growth / Reserve / Leaf / Flower / Fruit]
  → 夜间时间推进 [K uh]
  → 真实果实与材料 [E_free[7], Products[]]
  → 工作台加工：原果 / 剥壳 / 榨汁 / 料理
  → 委托交付 / 图谱发现 / 技术研究 / 样本收藏
```

植株领域计算复用 `../aquamelon-kitchen/02-data-and-balance.md`、`03-growth-and-harvest.md`、`04-elemental-reactions.md`、`05-sensory-identity.md`、`06-flavor-contract.md`。单对象状态及时间仍按已确定顺序进行，允许多个地块拥有各自合法 Soil/Plant 状态，但绝不共享一份隐式 Reserve。

## 2. 加工不允许复制物质账本

旧版快捷路径：一个完整 MatureFruit → 一个 AquamelonJuice，完整账本仅转移一次。

新增的剥壳、切分、料理必须设计自己的配方 `inputs[] -> outputs[]` 与物质分配规则。对同一物品，不能既保留完整果实又从它生成完整账本的果壳和果汁；处理后应消耗原对象，新物品取得独立 ID，七元素 G/反应产物以明示方式分配或转化。实际产率、剥壳损耗和料理反应仍待独立设计审查，不在本草案伪造公式。

P0 可以优先实现 **完整果实→单份果汁** 的保守旧路径，同时展示「剥壳台」为尚未开放的研究项；若要求 P0 真正剥壳，必须先批准最小物质分账合同，不能仅修改 UI。

现有七维数值/反应规则可维持不变；加工新增的是物品配方合同及明确的守恒/损耗语义，不应悄悄修改原有 Growth/反应公式。

## 3. 领域状态建议

```lua
Game = {
  day = 1,
  phase = "DAY_WORK",
  dayAdvanceUH = 24,     -- 候选 pacing，待验证
  dayCondenseUsed = 0,
  dayCondenseLimit = 0,   -- 初值由配置/技术决定
  plots = {},             -- 各自 Soil/Plant
  looseBalls = {},        -- 球有稳定 id 与 V
  items = {},             -- 材料、器具、料理有稳定 id
  machines = {},          -- 设备输入/输出和夜间进度
  visitors = {},          -- 当日访客/任务状态
  orders = {},
  discoveries = {},       -- completed + evidence
  tech = {},
  productionPlans = {},
  eventLog = {},
}
```

此结构用于标明单一状态所有权，不是强制实现为一个巨大模块。实际 Lua 模块按已有 Domain / UI / Taste 分离增加 Visitor / Discovery / Production / DayController，避免多套账本。运行时 GUI 只投影 Game，按钮调用经校验的领域动作。

日结顺序建议：
1. 验证结束日指令，快照运行中生产配置和库存；
2. 按时间顺序推进每个地块已有 `advanceUH(K)`，保留同一模型日界事件（如每日 04:00）及真正输入/反应的先后；
3. 用同一 K 推进设备生产工序；对完成的输入物料仅扣一次，生成合法产物；
4. 从发生的事件判定探索图完成，冻结报告及证据，更新可用科技/委托状态；
5. 原子写入次日状态并刷新 UI。失败时不得出现部分结算、重复领奖或材料复制。

具体领域/生产结算先后涉及设备消耗哪些活体产物，必须在配方设计时锁定，不可一概假定所有设备同于夜间最后结算。

## 4. P0 体验闭环建议

首个可玩切片目标：

- 一个 16:9 固定柜台，至少一位剧情仙人、一位后续访客；访客能递交种子及委托。
- 洞天管理终端有最少一个可种植地块；每天 N 次随机凝聚和可选择的浇灌动作。
- 玩家可手动结束日，结算 K uh；次晨可见真实 Growth 阶段和重要事件。
- 同一原有数值系统能生成至少一枚合法 MatureFruit，经工作台完成真实一果一汁加工与一次订单交付。
- 图谱至少覆盖「种子→种植→供给→生长→成熟→果汁→交付」及一个独立的隐藏反应节点；项目首批探索候选见 02 文档。
- 玩家经历重复收集后，可通过技术解锁一个有实效的便捷工具（P0 建议批量收集）。
- 每一个达成图谱条件的节点，都能够指出对应的真实游戏事件与证据。
- 至少一份「夜间结算记录」可以在 Debug 中复现其实际 Soil/Reserve/Growth/产物变化；不以 24 倍产量公式伪造结算。
- 完成新开档→接受种子→种植→多夜成长→收获→榨汁→交付→图谱发现的手动端到端验收。

**P0 明确延期**：大量料理配方、多格批量洞天、完整自动化、全部剧情仙人、200+探索节点、复杂经济、与外部 AI 联网、多人/服务端节点图。保留旧版果汁 AI 品尝提示词作为后续可接入功能，不要求为了新交互当即完成跨应用复制。

## 5. 平台与编辑器边界

本项目已实机验证：Lua 在 `ClientUIContainerControl` 宿主修改文本、PC 鼠标点击监听；Seed→Sapling 已有计算切片证据。未验证：大量可缩放图谱、稳定动态物品拖动、复杂层叠窗、动态图片替换、持久存档与高数量实体。因此 P0 应优先验证这些接口中最关键的 **界面视图切换、真实操作 ID、日结性能、存档**；若拖动不可用，采用选择物品→点击设备。

静态 UI、角色立绘、器具图片和位置由创作者在千星编辑器布置；Lua 管理状态、操作判定、时间推进和显示内容。禁止把 Web 前端、Node 后端或旧节点图编译流程引入当前纯 Lua 单机实现。

## 6. 设计关口

实现前仍需 Lead 锁定：
- `K` 与初始 `N`，据原有真实数值模拟首果天数、不同随机供给轨迹；
- 单个洞天地块与原单株状态的映射；
- 成就触发事件的最小契约、隐藏节点揭示规则；
- 第一批实际支持的加工配方与物质分账；
- 桌面物品/访客/窗口在千星 Lua 中的最小真实交互；
- 游戏日跨会话存档/读档的实际平台能力。
