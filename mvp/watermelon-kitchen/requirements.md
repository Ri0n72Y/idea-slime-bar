# 水瓜厨房

“水瓜厨房”是千星奇域版本的第一版 MVP，用来验证游戏最核心的一组玩法关系：

```text
长期培养水瓜树
↓
获得不同部位、形态和元素倾向的素材
↓
处理与组合素材
↓
生成不同的饮品和料理
↓
发现新的材料用途和组合结果
↓
反过来决定之后怎样培养和采集水瓜树
```

第一版重点验证植物培养、丰富素材和自由料理。生产线、自动化和完整经营系统暂不进入核心范围。

千星奇域水瓜树的世界设定见 [千星奇域水瓜树](setting.md)。原世界普通水瓜的基础形态与部位设定见 [水瓜 Aquamelon](../../docs/plants/aquamelon.md)。

## MVP 核心

### 一棵长期培养的水瓜树

玩家拥有一棵不会自然凋亡的水瓜树。

千星奇域版本不再以“收获果实、留种、重新播种”为主要循环，也不在第一版实现复杂育种。水瓜树持续存在，并重新生长可以采集的叶片、增生茎和果实。

玩家围绕同一棵树进行长期培养。

### 元素培养

水瓜树能够富集火、水、风、雷、草、冰、岩七种元素力。

这些元素数值是隐藏状态。正式玩家界面不提供元素 UI 或精确数值展示，玩家主要通过水瓜树和产物的颜色，以及制作后的口味和元素反应结果观察培养效果。开发阶段允许使用独立 Debug UI 直接查看和修改土壤、树体与器官状态，用于验证系统。

不同部位具有不同元素亲和倾向，同一棵树产生的果实、果壳、果肉、汁液、叶片和茎可以因此形成不同的元素表现。

第一版需要验证“浇灌不同元素资源会改变之后获得的素材”这一关系，但不要求在第一轮开发中一次完成七元素的全部性状、全部反应和完整数值模型。

第一版的核心培养模型已经调整为“土壤元素储备 → 树体吸收与内部 Reserve → Growth Tick → Growth Vector → 器官 Stage / 连续学习 / 表型”。具体见 [七元素养分与生长系统](growth-system.md)。元素颜色、口味、水草绽放与水瓜汁混合等下游规则继续见 [七元素培养与水瓜汁混合](elemental-cultivation.md)。旧版直接向树体浇灌、树体连续自然衰减和器官一次性快照规则不再作为当前实现依据。

### 素材与不同形态

水瓜厨房需要让同一种植物产生足够丰富、且彼此有明确 identity 的世界材料。当前不使用“同一个 Item + stage 字段”表示嫩叶、肥厚叶、青果和成熟果。

当前已经确认的活体器官 -> world Material：

| 活体状态 | Material | 中文 |
| --- | --- | --- |
| SmallLeaf | `TenderLeaf` | 嫩叶 |
| LargeLeaf | `ThickLeaf` | 肥厚的叶片 |
| 所属 Fruit Growth=100 后同步纤维化的 parent Leaf | `AquamelonLeaf` | 水瓜树叶 |
| Green Fruit，30<=Growth<100 | `GreenFruit` | 青果 |
| Mature Fruit，Growth>=100 | `Aquamelon` | 水瓜 |

`AquamelonLeaf` 不是叶片单纯放久后的时间成熟结果。Fruit Growth 达到 100 时：

```text
Green Fruit -> Mature Fruit
parent Leaf -> fibrous Aquamelon Leaf
```

二者在同一个成熟事件中发生。

采摘后：

```text
Living Organ
-> world Material
```

材料退出植物生长模拟，不再参与 Tree / Leaf nutrient allocation、organ Growth 或 on-tree enrichment。材料作为场景中的实际独立对象存在，可以直接放在地面；当前不设计传统背包、stack size、容器和拾取容量。

当前每个材料实例至少保留以下元素相关语义：

```text
MaterialType
ElementAmount[7]
Affinity[7]
```

`FlavorRatio[e] = ElementAmount[e] / sum(ElementAmount)`，仍是派生值而不是需要重复持久化的数据。不同材料可以拥有自己的元素属性、Affinity 和未来确有必要的特有数据；本轮不建立 generic material / item component framework。

当前已确认的最小加工关系：

```text
GreenFruit / 青果
-> GreenFruitPeel / 青果皮
 + GreenFruitFlesh / 青果肉

Aquamelon / 水瓜
-> AquamelonShell x2 / 水瓜壳
 + AquamelonJuice x1 / 水瓜汁

AquamelonShell
-> AquamelonFlesh / 水瓜肉
 + remaining shell material
```

`GreenFruitPeel` 有弹性；`GreenFruitFlesh` 为胶冻 / 凝胶质地，可表现青果内部混沌且尚未稳定分层的元素形态。`AquamelonShell` 是木质 / 硬壳的两个半球形独立材料；`AquamelonJuice` 是成熟水瓜的稳定液体产物；`AquamelonFlesh` 从成熟水瓜壳内侧剥出，有弹性、口感类似椰果。

`GreenFruitFlesh` 与 `AquamelonFlesh` 是不同材料；`GreenFruitPeel` 与 `AquamelonShell` 也是不同材料。成熟水瓜的“果壳 / 光滑内膜 / 果肉膜 / 清澈水瓜水”仍可作为生物形态描述，但不要求每个解剖层都成为可拾取 Material；当前不建立 generic `AquamelonPeel`，也不把 `AquamelonPulpMembrane` 锁成独立掉落。

加工会生成新的独立材料实体，但本轮不定义多个产物之间如何分配 `ElementAmount`、如何继承 / 改变 `Affinity`，也不定义加工 yield、质量守恒、品质、耐久、新鲜度或腐败。

水瓜茎、水瓜鬃等仍可作为原世界的长期材料背景，但不在这轮千星奇域 MVP 材料 identity 合同中重新定义。

### 自由组合料理

料理是第一版最重要的验证对象之一。

料理不以固定配方表作为唯一结果。玩家选择已经获得的不同素材进行组合，素材的部位、形态、加工程度和元素构成共同影响最后结果。

料理至少需要能够表现：

- 使用了什么素材
- 素材处于什么形态
- 主要元素倾向
- 最终颜色
- 味道
- 口感

料理名称和评价可以根据最终结果程序生成。

第一版的目标是验证这种“素材决定料理”的组合方式是否有趣，不要求一次完成完整的口味学、元素料理体系和所有可能组合。

## 交互

水瓜厨房继续使用现有的点击式劳动交互。

玩家不直接控制史莱姆移动，而是选择可交互对象和行动，由史莱姆自行移动到目标位置执行。素材作为场景中的实际物品存在，可以被采集、搬运和放到料理或处理位置。

具体规则见 [交互与劳动](interaction.md)。

第一版只实现培养、采集、素材处理和料理所需要的交互，不开发任务队列和自动化调度。第一条可见垂直切片优先做到“土壤供给 → 树体生长 → 叶片阶段 / 显色 → 点击采集 → 再生”。

## 顾客与水吧

水吧是料理展示和反馈的场景。

顾客可以用于表达需求、品尝玩家制作的饮品和料理，并对结果给出反馈。现有 [餐厅与顾客](../../docs/gameplay/restaurant.md) 中的未知需求、多轮尝试和顾客反馈可以继续作为参考。

第一版不要求完整实现餐厅经营、清洁压力、经济循环和大规模座位扩张。

顾客系统在 MVP 中需要做到多深，后续在料理玩法确定后再单独讨论。

## 多人方向

长期设计中，每个玩家拥有自己的水瓜树和水吧。

不同世界的水瓜树会因为培养方式、元素环境和隐藏互动影响产生不同特色。玩家访问其他世界，可以接触和获取当地具有特色的水瓜素材，再用于自己的料理。

多人互动还可能反过来影响水瓜树，但这些变化不直接以数值展示。

这一方向属于水瓜厨房的重要长期目标，但第一版是否需要真正实现跨世界访问、材料交换和隐藏互动，由后续 MVP 拆解决定，不作为当前的默认完成条件。

## 第一版明确不做

当前 MVP 不以以下内容为开发重点：

- 自动化生产
- 复杂生产线
- 史莱姆分身劳动
- 完整仓储和物流系统
- 普通水瓜的反复播种循环
- 复杂育种
- 正式科技树
- 大规模餐厅经营
- 完整经济系统
- 多地区探索
- 大量其他植物

[MVP 积分与解锁](../../docs/gameplay/progression.md) 属于此前用于延长原型可玩时间的实验方案，不再作为水瓜厨房第一版的核心要求。

## 当前完成标准

第一版至少需要证明以下关系能够形成可玩的闭环：

1. 玩家能够持续培养同一棵水瓜树。
2. 培养行为能够改变之后出现的水瓜素材。
3. 玩家能够从树上获得不同部位和不同形态的素材。
4. 素材能够继续处理并保留有意义的差异。
5. 玩家能够自由组合多个素材制作料理。
6. 料理结果会根据素材差异产生可观察的颜色、味道、口感或元素表现。
7. 玩家会因为想获得某种料理结果，而重新考虑下一轮怎样培养、浇灌和采集水瓜树。

当前文档固定第一版目标和范围。七元素培养与最小水瓜汁料理闭环已经进入可开发状态；顾客反馈、多人部分和更多料理内容继续按 MVP 实现顺序逐项设计，不在本阶段展开。
