# 编辑器边界

这个模板采用“代码优先”的开发方式，但并不意味着可以脱离编辑器独立完成全部功能。AI 应优先用代码实现玩法逻辑，同时清晰区分运行时逻辑与编辑器预先制作的资源和配置。

语言说明：
- 以中文协作时，优先阅读本文件。
- 若以英文协作，可配合 `docs/EDITOR_BOUNDARIES.md` 使用。

## 核心原则
- 优先用代码处理运行时逻辑：状态机、定时器、波次流程、经济结算、校验、创生/销毁、结算和信号编排。
- 不要假设编辑器资源一定已经存在。若某项功能依赖编辑器内预先制作的资源、组件、模板或 ID，必须明确指出。
- 不要仅根据 API 名称猜测编辑器能力；若工作区存在本地编辑器参考文档，应先查证。

## 必须在编辑器中完成的内容
- 场景与地图设置：地形、出生点、复苏点、导航、实体摆放、布局、装饰。
- 节点图容器与最终绑定：若采用自动注入，目标 NodeGraph 必须先在地图中创建并保存；若采用 `.gia` 手动导入，则不要求预先创建同 ID 的空目标图，但导入后的资源挂载、变量/结构体绑定和资源引用仍由编辑器完成。
- 元件 / 元件组 / 资产：建筑、敌人、掉落物、特效、UI 资源、音频资源、图标。
- 组件挂载与基础配置：组件需要先在编辑器里挂到实体或元件上，代码只能使用或调整已有组件。
- 路径、巡逻以及需要烘焙/预处理的导航相关内容。
- 界面布局、界面控件组、交互按钮、计时器控件、计分板控件。
- 千星沙箱中的信号定义。
- 全局计时器管理器中的全局计时器定义。
- 商店模板、货币定义、背包模板、商店组件。
- 能力单元、战斗预设及其他战斗侧预配置数据。
- 文本气泡、小地图标识、音效播放器、铭牌等表现资源。

## 通常更适合在代码中实现的内容
- 游戏阶段与状态切换。
- 建造 / 占位 / 解锁逻辑。
- 经济计算、奖励、价格、生产周期。
- 波次调度、刷怪顺序、存活数量统计。
- 运行时创建元件、移除实体、触发结算。
- UI 显隐切换、控件组激活、按钮事件响应。
- 信号收发与多实体协作。

## 关键边界说明
- 组件属于编辑器预配置内容。运行时代码可以切换或修改部分组件行为，但不应假设可以在局内动态添加或删除组件。
- 普通定时器可以直接在节点图中创建。
- 全局计时器必须先在编辑器中定义，代码只能按名称引用。
- `createPrefab` / `createPrefabGroup` 是在运行时创生已经制作好的元件资源，不是动态创建新的编辑器资产。
- 商店不是“空开”。要能正常使用，必须先有货币、商店模板、背包支持和商店组件。
- 若走标准攻击链路，则需要先在编辑器中配置能力单元；若缺失这些预设，代码可能需要退回到更简单的直接扣血方案。

## 节点图代码生成与编辑器边界

当前项目采用“TypeScript 生成节点图 + 编辑器完成资源绑定”的混合开发方式。节点图编译产物以运行语义正确为首要目标，不要求生成后的可视化布局与人工节点图同样易读。

### `.gia` 手动导入优先

- 已验证服务器节点图可以通过“TypeScript → 编译 → `.gia` → 编辑器手动导入”进入项目。
- 在这一工作流中，代码中的节点图 ID 主要服务于编译、合并或自动注入；手动导入时不应默认它必须与编辑器内既有图 ID 一一对应。
- 这一结论目前只适用于已经实际验证过的图类型。客户端图、过滤器、技能图等其他类型仍应逐类验证，不要推断所有 `.gia` 都完全忽略 ID。
- 自动注入仍然是可选能力，而不是默认开发前提。只有确实需要自动覆盖、批量同步或持续注入时，再引入地图 ID、目标图 ID 和空图安全检查。

推荐默认流程：

```text
编写 TypeScript
→ 编译生成 .gia
→ 编辑器手动导入
→ 完成资源/变量/结构体等手动绑定
→ 运行验证
```

### TypeScript 是算法逻辑的主要 source of truth

- 状态机、数值计算、循环、条件分支、运行时数据读写等逻辑优先维护在 TypeScript 中。
- `.gia` 和最终节点图主要视为编译产物，不要求开发者长期手工维护与源码完全一致的视觉布局。
- 评审生成图时优先检查“事件入口、数据来源、分支条件、循环边界、写回目标和最终结果”是否与设计一致，而不是要求节点位置和连线形态与人工图一致。

### 不把源码函数等同于独立子节点图

- `gstsServer*` 等源码级复用函数用于减少 TypeScript 重复，不代表编译后一定生成独立的子节点图资产。
- 编译器可能把多个源码函数展开或拼接到同一张节点图中，因此生成图可能出现长连线、重复取值节点和较差的人工可读性。
- 如果某段逻辑需要在编辑器中长期作为清晰、可复用、可单独调试的子图存在，应显式将其设计为编辑器侧节点图资产，而不是仅依赖 TypeScript 函数抽象。

### 编辑器手动绑定是正式开发步骤

当编译器无法安全表达某种编辑器结构时，不应为了“全代码化”而退化数据设计。以下内容可以作为正式的手动绑定边界：

- 自定义结构体及其动态字段；
- 依赖地图内具体结构声明才能确定引脚的节点；
- 元件、挂接点、组件、表现资源和预设；
- 需要编辑器上下文才能确定的实体、资源或配置引用；
- 编译器当前缺少可靠类型支持的动态节点参数。

代码中可以临时使用明确标注的占位值或桥接数据来完成算法验证，但最终版本必须记录需要在编辑器中替换或绑定的部分，避免把实验常量误当成正式配置。

### 生成图的评审原则

对自动生成的节点图，按以下顺序检查：

1. 运行语义是否与设计一致；
2. 列表索引、循环起止和类型转换是否正确；
3. 自定义变量、实时列表引用和写回语义是否正确；
4. 编辑器手动绑定部分是否明确；
5. 只有在需要人工长期维护节点图时，才进一步优化可视化布局和模块拆分。

不要为了让自动生成图“看起来像人工图”而增加没有运行价值的局部变量、重复节点或额外抽象。

## 特性开发流程

本项目对单个特性采用“实体职责先行、节点图小型化、复杂计算显式复用”的开发流程。

这一组织方式与主流游戏编辑器的组件化 / 场景化工程习惯一致：先确定对象及其职责，再把行为拆成可维护的小单元；可复用、无状态或高复杂度的逻辑进一步抽离，而不是持续堆叠在单一事件图中。

### 1. 先做实体分解

开始实现一个特性前，先明确该特性需要哪些实体。每个实体至少记录：

- 实体名称与用途；
- 它在该特性中承担的单一职责；
- 它拥有的运行时属性 / 自定义变量；
- 它依赖的编辑器资源、组件、挂接点、预设或其他实体；
- 它需要接收或发出的事件 / 信号；
- 哪些状态归它自己维护，哪些状态属于其他实体或关卡全局。

避免先从“要画哪些节点”开始。节点图应当从实体职责自然推导出来。

### 2. 再按职责设计节点图脚本

每个节点图脚本应尽量满足：

- 功能单一；
- 输入和输出明确；
- 对应一个简单流程；
- 状态所有权明确；
- 不同时承担多个不相关阶段的编排、计算和表现职责。

一个脚本通常只负责一个事件入口或一个清晰的状态转换。例如：初始化、接收输入、应用一次结算、生成一个对象、推进一个阶段。

### 3. 复杂流程拆成多个脚本

如果一个流程包含多个明显阶段，不把它继续扩成一张大图，而是拆成多个节点图脚本，由事件、信号、状态变量或实体关系进行编排。

典型情况包括：

- 初始化流程包含读取持久状态、离线结算、状态修复和后续生成；
- 一个实体既要处理输入，又要生成其他实体，还要维护生命周期；
- 一个流程存在多个可独立验证的阶段。

拆分标准不是机械限制节点数量，而是每个脚本是否还能被一句话准确描述其职责。

### 4. 复杂数学计算单独建立节点图

复杂数学公式、可复用数值变换或需要人工确认连线正确性的计算，不直接内联到主流程生成图中。

处理方式：

1. 单独创建一个只负责该计算的节点图文件；
2. 通过 TypeScript / genshin-ts 生成 `.gia`；
3. 手动导入编辑器；
4. 在编辑器中打包为复合节点；
5. 复合节点名称与该节点图文件名保持一致。

例如：

```text
element_decay_calc
```

则文件、导入节点图和最终复合节点都统一使用 `element_decay_calc` 这一名称。

复杂数学节点图应尽量保持纯计算语义：输入明确、输出明确，不主动承担外部实体状态编排。

### 5. 主流程通过手动接入点调用复合节点

当主流程需要调用上述复合节点时，不让 genshin-ts 再次把复杂公式展开进主图。

生成脚本应在调用位置保留一个简单、容易识别的占位节点，并明确标注需要手动接入的复合节点名称。注释必须直接引用对应节点图文件名，例如：

```text
MANUAL: connect compound node element_decay_calc
```

编辑器侧完成导入后，将该占位位置替换或连接到同名复合节点。

占位节点的具体技术实现必须使用 genshin-ts 已确认可生成且不会改变正式运行语义的节点；在这一实现方式尚未固定前，不得自行假设某种 no-op / comment 节点存在。

### 6. 一个特性的标准交付拆分

后续开发一个具体特性时，默认按以下顺序输出：

```text
Feature
├── Entities
│   ├── Entity A
│   │   ├── Responsibility
│   │   ├── Runtime Properties
│   │   └── Editor Bindings
│   └── Entity B
│       ├── Responsibility
│       ├── Runtime Properties
│       └── Editor Bindings
│
├── NodeGraph Scripts
│   ├── simple_flow_a.ts
│   ├── simple_flow_b.ts
│   └── simple_flow_c.ts
│
├── Reusable Compound Graphs
│   └── complex_math_calc.ts / .gia
│
└── Manual Editor Work
    ├── import .gia
    ├── package compound nodes
    ├── connect marked call sites
    └── bind assets / structures / components
```

### 7. 审查标准

一个特性在进入实现前，应先能回答：

- 有哪些实体？
- 每个实体只负责什么？
- 状态由谁拥有？
- 每张脚本图能否用一句话描述？
- 是否存在应该独立成复合节点的复杂数学计算？
- 哪些地方必须由编辑器手动绑定？
- 主流程中所有手动接入点是否都标出了明确的复合节点文件名？

如果一张生成图同时承担多个阶段、出现大量跨区长连线，或必须理解整张图才能判断某个局部功能，应优先重新拆分，而不是继续在同一张图上增加节点。

## AI 工作规则
- 对任何功能需求，都应显式拆成：
  - 代码改动
  - 仍需手动完成的编辑器配置
- 若受限于缺少编辑器配置，不要默认其存在；应明确指出缺了什么。
- 做设计时，优先选择“尽量由代码驱动、但不越过编辑器边界”的方案。
- 若工作区内有本地编辑器参考文档，优先以其为准，再对编辑器行为做判断。
- 若用中文回答，应优先沿用中文文档中的官方或社区常用术语，不要临时直译英文术语。

## 建议回答格式
- 先说明哪些部分现在就可以用代码实现。
- 再列出最小编辑器配置清单。
- 最后说明对 ID、模板、预挂组件、资源等的假设。
